> case-study // nicu-network // private repo

Getting a sick newborn to the right bed, in time

NICU Network is a digital referral and coordination platform for neonatal intensive care, built for the Digital Healthcare Access Foundation's 2026 pilot in Abuja. When a newborn needs specialist care, referring clinicians today phone hospital after hospital looking for a free cot. The platform shows live bed availability across a network, routes each referral to the hospitals that can actually take the baby, and gives a 24/7 coordination team the tools — and the audit trail — to make sure nothing falls through the cracks.

01 The problem

A coordination failure, not a capacity one

Nobody can see the beds

Neonatal capacity changes hour by hour and lives in each unit's head. Referrers find out by phone, one hospital at a time, while the baby waits.

Clinicians must decide

The system can't just assign a hospital. Receiving teams need to offer a bed, and referrers need to choose between offers with the clinical picture in mind.

Accountability is clinical

Every escalation, call and handover may be reviewed later. The record has to be complete and impossible to quietly rewrite.

Not every hospital is online

Some facilities can't use an app at all. The process still has to work for them — by phone, through people — without breaking the data.

03 Architecture decisions

Decisions that carry clinical weight

  1. ADR-01

    An API owns the rules; the database is the safety net

    Decision
    All writes go through a FastAPI service that verifies the user's token and role. Supabase supplies authentication, Postgres and realtime; row-level security and database functions guard the data underneath.
    Why
    Referral rules — who can see a referral, which transitions are legal, when a bed is held — are too important to spread across a browser app. One service is easier to reason about, test and audit, while database-level guards still hold if the API has a bug.
    Trade-off
    A second deployable to run, and an extra hop on every request compared with talking to Supabase directly.

  2. ADR-02

    Broadcast-and-offer matching, not automatic assignment

    Decision
    A new referral is sent only to hospitals with a free bed of the right unit (NICU or SCBU), the right type (inborn or outborn) and a suitable level of care. Each hospital can offer a bed; the referring clinician chooses between offers.
    Why
    It mirrors how clinicians already work, keeps the decision with the people accountable for it, and cuts out hospitals that would only say no.
    Trade-off
    Slower than auto-assigning the nearest bed, and it needs offers to expire cleanly when another hospital is chosen.

  3. ADR-03

    An explicit state machine for every referral

    Decision
    Referrals move through defined states — pending, offered, accepted, confirmed, in transfer, arrived, completed — and the API rejects any transition that isn't allowed. Accepting holds a bed in the same step.
    Why
    A baby can't be "arrived" before it was "in transfer". Making the lifecycle explicit turns whole classes of bugs into clear errors, and makes the audit trail readable.
    Trade-off
    Real-world exceptions need deliberate new transitions rather than quick edits.

  4. ADR-04

    Make the audit trail tamper-proof in the database

    Decision
    Case events, call logs and reported outcomes are append-only: database triggers reject any update or delete. Generated reports are frozen snapshots. Hospital status notes are never edited — they can only be marked "no longer current", once.
    Why
    In clinical governance the record is the product. Enforcing it in Postgres means no application bug, admin tool or future feature can quietly rewrite history.
    Trade-off
    Mistakes are corrected by adding new events, never by editing old ones — which the interface has to make easy.

  5. ADR-05

    Race-safe case claiming

    Decision
    Claiming a case is a single database function: it checks the officer's role and active shift, then assigns the case only if it is still open and unclaimed, recording the claim as an event in the same step.
    Why
    Two officers clicking the same urgent case at the same moment must never both believe they own it. A conditional update makes the database the referee: exactly one wins, the other gets a clear message.
    Trade-off
    Business logic lives partly in SQL, so it's versioned and reviewed with the migrations.

  6. ADR-06

    Privacy by default for family contact details

    Decision
    A family's phone number is stored for welfare checks but withheld from other hospitals until clinical confirmation. Inside the coordination console it stays hidden until an officer reveals it — with a reason code and a note, logged as an audit event.
    Why
    Data minimisation: people see personal data only when they have a reason, and every access is accountable.
    Trade-off
    One extra step for officers in a hurry; the reason codes keep it to a couple of taps.

  7. ADR-07

    Model the 24/7 operation, not just the data

    Decision
    Coordination is organised around 12-hour shifts in local time. Officers must be on shift to work a case; handovers keep ownership with the outgoing officer until someone accepts; reopening a closed case needs the coordination lead's approval. Critical alerts become urgent cases automatically, via a database trigger.
    Why
    Most failures in round-the-clock services happen at the seams — between shifts, between people. Making those seams explicit means a case is never ownerless.
    Trade-off
    More process in the software, which only works if it matches how the team actually operates — so each rule traces back to a numbered section of the operations spec.

  8. ADR-08

    Design for hospitals that can't use the app

    Decision
    "Relayed" referrals let a coordination officer hold one or both clinician sides of a referral by phone. They run in their own queue and never raise urgent alerts.
    Why
    Excluding offline facilities would exclude the babies they care for. The relay keeps them in the same process and data model, while suppressing alerts avoids flooding the team with noise about cases it is already handling.
    Trade-off
    Data for relayed cases is only as good as what's captured on the call.

  9. ADR-09

    Realtime as a signal, the API as the source

    Decision
    The app subscribes to database changes on beds, referrals and alerts, but uses each event only to invalidate cached queries, which then refetch through the API. Tokens are verified locally against Supabase's published keys, with a fallback for the legacy signing method.
    Why
    Screens update within moments of a bed freeing up, but every byte the user sees has still passed the API's permission checks. The token fallback kept sign-in working through Supabase's move to new signing keys.
    Trade-off
    A refetch per change is chattier than pushing data directly — fine at pilot scale, and the first thing to revisit at network scale.

04 Known limits & roadmap

What I'd harden next

  1. 01Move bed holds into a single atomic database operation, so two simultaneous acceptances can never double-book the last cot.
  2. 02Use per-request, user-scoped database access in the API so row-level security applies on every query, not only as a backstop.
  3. 03Replace per-hospital lookups in bed matching with one joined query as the network grows beyond the pilot.
  4. 04Add SMS alerts for hospitals with poor data coverage, and an automated test suite for the referral and coordination rules in CI.
