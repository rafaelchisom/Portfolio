> case-study // oyaquiz.com

A live multiplayer game with no game server

Oya Quiz is a party quiz in the style of the big classroom games: the host puts questions on a TV, everyone answers on their phone against the clock, and the leaderboard updates between rounds. Players can also type any topic and get a fresh AI-written round. I built it in five days, with no game server: the rules, the clock and the scoring all live in Postgres.

02 Architecture decisions

Fair, fast, and cheap to run

  1. ADR-01

    Secret tokens instead of accounts

    Decision
    Creating a game returns a host token; joining returns a player token. Tokens live in tables nobody can read, and every action has to present the right one.
    Why
    A party game dies at the sign-up screen. Tokens give zero-friction joining with a six-digit code, while still making it impossible to answer as someone else or run another person's game.
    Trade-off
    Lose the token and you lose your seat — acceptable for a game that lasts twenty minutes.

  2. ADR-02

    Tables are read-only; every move is a database function

    Decision
    The public can read game state, but all writes go through five functions: create, join, advance, answer and leave. The game is a small state machine — lobby, question, reveal, leaderboard, finished — that only the host's token can move forward.
    Why
    With no server of my own, the database had to be the referee. Functions make every rule — name length, unique names per game, legal state changes — impossible to bypass from the browser.
    Trade-off
    Game logic lives in SQL, which is less familiar to most front-end developers; the setup script is commented line by line and safe to re-run.

  3. ADR-03

    Score on the server's clock, not the player's

    Decision
    Answer time is measured by the database from the moment the question opened, with a 1.5-second grace window for network lag. Correct answers earn 1,000 points falling to 500 as time runs out, plus a streak bonus capped at +500. Each player can answer each question exactly once, enforced by the table's primary key.
    Why
    Anything measured in the browser can be faked. Server-side timing makes speed honest, the grace window keeps it fair on slow connections, and the key turns double-tapping into a no-op instead of a bug.
    Trade-off
    Players on very slow networks lose a little time to latency — the grace window covers typical cases.

  4. ADR-04

    Realtime keeps every screen in lockstep

    Decision
    The TV and every phone subscribe to changes on the game, players and answers. A "remote" mode shows the whole game on each phone, for groups that aren't in the same room.
    Why
    When the host moves to the next question, every screen changes at once — the feel of a live game show, with no websocket server to build or host.
    Trade-off
    Change events are public for game tables, so anything sensitive has to stay out of them (see the roadmap).

  5. ADR-05

    AI rounds behind a server function with a strict schema

    Decision
    "Make a category with AI" calls an Edge Function that holds the OpenAI key and requests output against a strict JSON schema. Every question is then validated — exactly four options, a valid answer — and anything malformed is dropped. The app reminds the host to check questions before playing.
    Why
    Keys never reach the browser, and a schema plus validation means a bad model response can't break a live game in front of a room of people.
    Trade-off
    A round takes a few seconds to generate, so it's made in setup, not mid-game.

  6. ADR-06

    Three layers of AI cost control

    Decision
    Daily limits per device, per network and for the whole site, checked and counted in one atomic database call. Networks are stored only as hashes — never raw IP addresses. Failed generations are refunded, the host has a code that skips limits, and if the limits can't be checked the function refuses rather than spending.
    Why
    A public "generate anything" button is an open invitation to run up a bill. The atomic check stops two simultaneous requests both slipping past the cap, and refunds mean outages don't punish users.
    Trade-off
    Shared networks, like a school or office, share one network allowance.

  7. ADR-07

    Analytics that can't slow the game or leak

    Decision
    Database triggers copy games, players and answers into private, append-only stats tables that survive when games are deleted. A dashboard reads them through one function that checks a bcrypt-hashed passcode; AI usage is logged on a best-effort basis that never blocks a reply.
    Why
    Questions like "which ones are too hard?" and "what topics do people ask the AI for?" need history, but gameplay must never wait on analytics, and none of it should be public.
    Trade-off
    One dashboard user with a passcode, not per-person accounts — right-sized for a solo product.

03 Known limits & roadmap

What I'd harden next

  1. 01Move correct answers out of the publicly readable game record into a private table, released only at the reveal — so a determined player can't look them up mid-question.
  2. 02Rate-limit game creation and joining the way AI rounds already are.
  3. 03Give Oya Quiz its own database schema instead of a shared project with name prefixes.
  4. 04Add automated tests for the scoring and game-state functions, run against a throwaway database on every change.
