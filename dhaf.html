> case-study // dhafinitiatives.org

Re-platforming a non-profit onto a shared, regulated data estate

The Digital Healthcare Access Foundation received a new website and CMS built for cPanel and MySQL. Its infrastructure was Render and a Supabase Postgres project already holding another programme's patient data. As IT Lead, I owned getting it live safely: no new database engine, no risk to the existing data, and a site that holds up on a phone.

01 Context & constraints

The problem behind the brief

Wrong database engine

The vendor package spoke MySQL only: ENUMs, ON DUPLICATE KEY, SQL_CALC_FOUND_ROWS, double-quoted strings. The organisation runs on Postgres.

A shared project with patient data

The only available Supabase project also served the NICU Network app — patients, hospitals, referrals. Name collisions with old tables, and a hard rule: touch nothing.

Ephemeral compute

Render's filesystem resets on every deploy. The installer wrote config, .htaccess and uploads to disk; all of it would vanish.

A front end with no source

The public site shipped as a compiled bundle. It hid its navigation on phones and lost scroll position between pages; there was no source to fix.

03 Architecture decisions

Eight decisions, and their trade-offs

  1. ADR-01

    Port the application to PostgreSQL instead of adding MySQL

    Decision
    Translate the schema and every query: ENUMs to CHECK constraints, ON UPDATE timestamps to triggers, upserts to ON CONFLICT, FOUND_ROWS() to explicit counts, case-insensitive matching made explicit with ILIKE/LOWER().
    Why
    One data platform to operate, back up and secure. A second engine for one website is permanent operational cost.
    Trade-off
    Diverges from the vendor's upstream. Mitigated by keeping migrations one-to-one with theirs, so future vendor releases map file-for-file.

  2. ADR-02

    Isolate with a schema and a least-privilege role, not a new project

    Decision
    Create schema dhaf owned by a dedicated login role whose search_path is pinned to it. Nothing in public is dropped, renamed or granted.
    Why
    The plan's project limit was reached, and the obvious shortcut — dropping the old site's tables — sat next to patient records. Isolation removed the risk instead of managing it. I verified it: the website's role gets permission denied on the patient tables.
    Trade-off
    The site still shares compute with the clinical app. Documented as a follow-up: move to a dedicated project when budget allows.

  3. ADR-03

    Turn on row-level security everywhere, with no policies

    Decision
    Enable RLS on all 22 tables in a dedicated migration.
    Why
    Supabase auto-exposes tables through its Data API to anyone holding the public key — including password hashes. The site connects as the table owner, which RLS doesn't restrict, so the API is closed with zero application change.
    Trade-off
    Every future table needs the same line; the migration header says so.

  4. ADR-04

    Design for the transaction pooler: no session state

    Decision
    Client-side (emulated) prepared statements, and INSERT … RETURNING id in place of every lastInsertId() call.
    Why
    In transaction mode, consecutive statements can land on different backend connections. lastval() could silently return another request's id — a data-integrity bug that only appears under load.
    Trade-off
    Emulated prepares give up server-side plan caching; negligible at this scale.

  5. ADR-05

    Replace the web installer with an idempotent bootstrap

    Decision
    On every container start: apply pending migrations, import starter content on a fresh database, and create the first admin from environment variables — all in one transaction under a Postgres advisory lock.
    Why
    The cPanel installer wrote state to a disk Render wipes, and a public install page is an attack surface. Transactional DDL means a failed first install leaves nothing behind; the lock stops two instances migrating at once during zero-downtime deploys. It also refuses to run against a database that already holds another app's tables.
    Trade-off
    Start-up does a little database work on each boot; it is a no-op once up to date.

  6. ADR-06

    Move uploads to object storage

    Decision
    Images are resized on upload, then pushed to a public Supabase Storage bucket; URLs are built in one helper so storage can change without touching controllers.
    Why
    Local uploads would disappear on the next deploy. A paid persistent disk would also pin the service to one instance.
    Trade-off
    A network hop per upload, and a service key to protect — held only in Render's environment.

  7. ADR-07

    Reuse database connections, and bound them

    Decision
    Persistent connections per Apache worker, with the worker pool capped at 25 and a short keep-alive.
    Why
    I measured ~1.1s per API call. The cause was geography: compute in Oregon, database in Ireland, and a fresh TLS handshake to the pooler on every request. Reusing connections removed the handshake; capping workers keeps the connection count predictable on a pooler shared with a clinical app.
    Trade-off
    Cross-Atlantic latency per query remains. The real fix — co-locating compute in the EU — is the planned next step.

  8. ADR-08

    Fix a sourceless front end by progressive enhancement

    Decision
    Layer a small stylesheet and script over the compiled bundle: an accessible mobile menu that reuses the app's own router links, scroll-to-top on navigation, and a delayed loading state. Assets are versioned for cache-busting.
    Why
    Rebuilding a vendor app without its source was out of scope. Diagnosing the scroll bug meant tracing it to the app's smooth-scroll CSS turning a reset into a slow glide — the fix requests an instant scroll and keeps the override until the browser applies it.
    Trade-off
    The overlay is coupled to the bundle's class names. A new vendor build must be re-checked; the README says exactly what to keep.

04 Results & verification

Shipped, measured, verified

  • Live on the organisation's own domain with HTTPS and a www-to-apex redirect, configured without disturbing the domain's Microsoft 365 email records.
  • API latency cut ~70%, from ~1.1s to ~0.35s, measured on the live site before and after.
  • Zero changes to the clinical app's data. Isolation was tested by trying to read patient tables as the website's role.
  • Every page usable on a 390px screen: no horizontal overflow, a working mobile menu, and pages that open at the top.

How it was verified

Each change ran against a disposable Postgres in Docker: about 70 end-to-end API checks covering auth, two-factor setup, CRUD, uploads, revisions, rate limits and login lockout, plus a guard test proving the bootstrap refuses a foreign schema. Layout was audited in headless Chrome at phone width on every page, then re-measured in production after each deploy.

05 What I'd do next

The roadmap

  1. 01Move compute to Render's Frankfurt region, next to the database — near-instant responses.
  2. 02Give the website its own Supabase project, ending the shared blast radius with the clinical app.
  3. 03Run the end-to-end suite in CI on every push, and gate deploys on it.
  4. 04Send transactional email through a dedicated provider with DKIM, since the Microsoft 365 mailbox no longer offers SMTP sign-in.
