> case-study // gym-log // private repo

A social fitness app with no server to run

Gym Log is an installable web app for a group of friends to log workouts, keep streaks, set monthly goals, compete on a leaderboard and nudge each other to train. I built it to need no backend server at all: the browser talks straight to Postgres, so the database itself has to be the security model.

Role
Sole designer and developer
Stack
Vanilla JS PWA · Supabase Auth & Postgres · row-level security · SQL functions
Features
Sessions & exercises · timer · tags · streaks · goals · leaderboard · nudges

01 Architecture

The database is the backend

02 Architecture decisions

Small app, serious boundaries

  1. ADR-01

    No backend server: the browser talks to Postgres

    Decision
    A static, installable web app using Supabase for sign-in and data, with no API layer of my own.
    Why
    Zero servers to patch, scale or pay for, and changes ship in seconds. For a friends-sized app, an API layer would be cost without benefit.
    Trade-off
    Anyone can call the database with the app's public key, so nothing can rely on the front end behaving. The next three decisions exist because of this one.

  2. ADR-02

    Row-level security as the authorisation layer

    Decision
    Every table has row-level security. Sessions, exercises and goals are readable and writable only by their owner; a nudge can only be sent as yourself, read by its recipient, and marked seen by them. Check constraints bound the data, such as session length.
    Why
    With no server in the middle, the database is the only place a rule can be guaranteed.
    Trade-off
    Policies must be designed table by table — and they interact with views in ways that bite (see the next decision).

  3. ADR-03

    Shared views come from functions that return only totals

    Decision
    The leaderboard and the admin dashboard are security-definer functions: they can read everyone's rows inside the database but return only aggregates.
    Why
    The first leaderboard was a view, and it inherited row-level security — so each person saw a leaderboard of one. Rather than loosen the policies, I moved the aggregation into a function, so no one's individual workouts ever leave the database.
    Trade-off
    Security-definer functions run with elevated rights, so they must return only what they need to and pin their search path. The admin functions already do; the leaderboard function is next on the list.

  4. ADR-04

    An admin list nobody can read

    Decision
    Admins are listed in a table with row-level security enabled and no policies — invisible to every client. A function answers only "is the current user an admin?", and the insights function checks it before returning anything.
    Why
    The admin list can't be enumerated or edited from the app, and there is no client-side flag to tamper with.
    Trade-off
    Admins are added in the database console, which is fine for one or two people.

  5. ADR-05

    Privacy-light usage telemetry

    Decision
    One small event per app open: event name, app version, platform, and whether it is running as an installed app. The user is stamped by the database from the session, not sent by the client, and every field is length-checked.
    Why
    Enough to see adoption and whether people install it, without tracking behaviour — and nobody can log events as someone else.
    Trade-off
    Deliberately shallow: it answers "is it used?" rather than "how?".

  6. ADR-06

    Installable, but never stale; and data integrity you can audit

    Decision
    A web manifest makes it a home-screen app, while the app shell is served with no-cache headers so every update reaches every phone immediately. When the leaderboard looked gamed, I investigated with read-only queries — sessions per day, future dates, and gaps between entries — before changing any rules.
    Why
    Fast iteration without "have you tried reinstalling?", and fairness disputes settled with evidence.
    Trade-off
    No offline mode yet; the app needs a connection to log a session.
